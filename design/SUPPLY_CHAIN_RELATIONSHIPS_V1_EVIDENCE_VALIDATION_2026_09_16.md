Verification was performed by four parallel research passes, one per company cluster, each required to fetch real primary documents (SEC EDGAR full-text search, direct filing URLs, official IR/newsroom pages) and quote exact text, or explicitly report "NOT VALIDATED — no accessible primary source found" rather than infer from general industry knowledge. Every quote, URL, filer, CIK, and accession number below was retrieved this session, not carried over from the prior discovery document's own unverified candidate list. **The result: 12 of 22 candidates survive strict Tier A verification — below the 15-relationship target range.** Per this task's own explicit instruction ("Do not lower the standard just to fill a category quota"), the shortfall is reported honestly rather than closed by admitting weaker evidence; see §4 for the full reasoning.

## 4. Evidence-standard decision log

1. **The eligibility rule as given in this task ("supported by at least one Tier A primary source") is stricter than the general evidence ladder proposed in the prior discovery document**, which explicitly allowed Tier B/C for COMPETITOR-type claims (reasoning: competitive-set claims are typically analyst/market-structure knowledge, not something either party discloses about itself). This task's own eligibility rules make no such carve-out. Applied strictly and consistently, **zero COMPETITOR-type candidates enter the v1 cohort** — including Hanwha Aerospace/KAI, whose only evidence is Tier B trade press. This is flagged as an open policy question for whoever finalizes the persisted evidence ladder: should COMPETITOR keep its Tier B/C allowance from the discovery document, or should this task's stricter Tier-A-only bar become the permanent v1 policy? Not resolved here — resolving it retroactively to admit Hanwha/KAI would itself be "lowering the standard to fill a category quota," which this task explicitly prohibits.
2. **Two candidates were rejected specifically because the primary evidence contradicted the hypothesis** (Fabrinet/Coherent, Ciena/Marvell) rather than merely being silent on it — a stronger, more informative rejection reason than "not found," worth distinguishing in any future candidate-sourcing process (a wrong guess is not the same failure mode as an unconfirmable one).
3. **A real evidence record existed but for the wrong relationship type** in exactly one case (Nabtesco/FANUC — shareholding, not supply) — this candidate is not merely "not validated," it's "validated for a different claim than the one proposed." Recorded distinctly in §3 rather than lumped in with the true not-validated cases.
4. **An entity-precision mismatch** disqualified Hanwha Aerospace/KAI even before the Tier A question arose — the best available evidence names a sister company. This is a distinct failure mode from "no evidence" or "wrong type," worth its own category for a future candidate-sourcing methodology: verify the *exact legal entity name* the evidence supports before proposing the candidate, not just the general corporate family.
5. **Two candidates (Vertiv/CoreWeave, Applied Materials/Samsung) were kept in the cohort despite real caveats** (one-sided/market-color framing; a since-changed disclosure practice) rather than rejected outright, because the underlying evidence is still genuinely Tier A, dated, and named — the caveats are recorded transparently in the cohort table's own `status`/`confidence` columns rather than hidden, consistent with "clear uncertainty language" being a first-class product requirement, not just an inference-time concern.
6. **The final count (12) is honestly below the 15–25 target.** Reaching 15 without lowering the standard would require sourcing genuinely new candidates (e.g., Eaton→NVIDIA/Siemens Energy/Flexnode, all three of which have real named Tier A evidence per the Eaton research pass, just not among the 22 originally proposed) — this is explicitly out of scope for this task, which was bounded to evaluating the original 22, and is recommended instead as the natural first step of a follow-up candidate-sourcing round.

## 5. Relationship-direction and reciprocal-display policy

- **FOUNDRY direction**: `source_entity` = the foundry, `target_entity` = the customer (e.g. `TSM → NVIDIA`). This follows the uniform convention already established in the discovery document — "source_entity is the [TYPE] of target_entity" — applied consistently to every directional type in this cohort, not a special case for FOUNDRY alone.
- **Canonical display wording**: on the foundry's own page: *"Foundry for [target]."* On the customer's page (the reciprocal view of the same single stored edge): *"Foundry: [source]"* or *"Fabricated by [source]."* The same pattern applies to every directional type in this cohort — e.g. INTEGRATOR (`CoreWeave → NVIDIA`) displays as *"Integrates: NVIDIA"* on CoreWeave's page and *"Integrated by: CoreWeave"* on NVIDIA's page; INFRASTRUCTURE_PROVIDER (`Vertiv → CoreWeave`) displays as *"Provides infrastructure to: CoreWeave"* / *"Infrastructure from: Vertiv."*
- **Storage vs. rendering**: every relationship in §2 is stored as exactly **one** edge row. The reciprocal label shown on the counterparty's page is derived at render time from `(relationship_type, direction, which entity is currently being viewed)` — never a second, duplicate edge row for the reverse direction. This is a hard rule, not a style preference: storing both directions as separate rows would immediately create a real dedup/consistency risk the moment one side's status changes and the other doesn't.
- **One evidence source supporting multiple directionally distinct edges**: permitted, but only when the source document itself discloses multiple distinct facts, each with its own excerpt. None of the 12 cohort entries needed this in practice — every evidence document here supported exactly one edge — but the policy is stated for future candidates: a single joint press release that discloses, say, both a supply relationship AND a separate partnership would produce two evidence records (same URL, two different excerpts, two different `relationship_id`s), never one evidence record loosely covering two claims.

## 6. Evidence freshness / revalidation policy

Applied concretely to this cohort, not just abstractly:

- **FOUNDRY, SUPPLIER, MANUFACTURER, INTEGRATOR** (9 of the 12 cohort entries): revalidate **annually**, or immediately upon either endpoint's next 10-K/20-F, whichever is sooner. **Concrete example already surfaced in this pass**: Applied Materials' *current* 10-K no longer names Samsung by name (it anonymizes customers as "CustomerOneMember" in XBRL tags) — the cited evidence is from the prior fiscal year's filing. This is exactly the scenario the freshness policy exists to catch: the relationship may well still be true, but the *disclosure practice itself* has degraded, and any future automated revalidation check must re-confirm against the company's *current* filing, not assume last year's named disclosure still holds.
- **INFRASTRUCTURE_PROVIDER** (Vertiv→CoreWeave, GE Vernova→Amazon): revalidate upon disclosed capacity expansion/contract-renewal news, or annually absent such news — infrastructure agreements are typically multi-year, so a fixed short cadence would generate needless re-review churn.
- The Redwire→Intuitive Machines edge is a special case: it is **mission-specific** (named to IM-2), and its own natural "freshness" question is not a calendar interval but "has a subsequent mission announcement named the same or a different camera supplier?" — recorded as its own explicit revalidation trigger in §2 rather than forced into a generic annual cadence.
- **Universal rule, restated from the discovery document and directly informed by this validation pass**: an edge whose supporting evidence is stale relative to its type's own freshness window caps the confidence any second-order inference built on it can reach — it is never silently treated as still fully current. The Applied Materials/Samsung and Lumentum/Cisco entries in §2 are both explicitly flagged this way.

## 7. v1-to-Postgres graduation criteria

An edge (or the cohort as a whole) should graduate from the YAML seed layer to a normalized Postgres table only once **all** of the following are true — not automatically at a fixed calendar date:

1. Every edge in the YAML cohort has completed at least one full revalidation cycle per its own type's cadence (§6) — proving the review process itself works in practice, not just at creation.
2. At least one real second-order inference has been manually constructed and reviewed end-to-end using a v1 edge (even performed manually, outside any automated engine) — proving the data shape actually supports the intended use case.
3. The cohort has grown, or is concretely expected to imminently grow, beyond what a single hand-maintained YAML file can be safely and legibly reviewed at — recommended threshold: roughly 50-75 edges, based on this codebase's own precedent (the 13-theme YAML registry stays legible at its current size; a relationship file with hundreds of entries would strain the "git diff is the audit trail" property that makes YAML the right v1 choice).
4. A concrete, separately-approved product need exists for programmatic (not just PR-reviewed) writes to the relationship data — e.g. a human-review workflow UI that needs to create new candidate edges outside a git-commit cycle.
5. Local Postgres test-ability is confirmed resolved — this exact session has repeatedly found no local disposable Postgres instance available, meaning a migration's own tests would be unverifiable in this environment today; graduation should not proceed until this operational gap is closed.
