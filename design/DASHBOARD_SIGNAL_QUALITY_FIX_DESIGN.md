# Dashboard/Signals Quality Fix — Design Proposal

Status: research/design only, no code changed. Scope: Daily News editorial admission (Issue 1), Daily News issuer-lane cross-language deduplication (Issue 2), and Daily News non-English translation controls (Issue 3). Does not touch EDGAR/DART/EDINET filing admission, promotion, ingestion credentials, workers, deployment, or production data.

**Page-naming note, confirmed by reading `src/ui/ui.py`'s own `PRIMARY_NAV`/`SECONDARY_NAV` tables:** the app's own "Signals" nav label (`("daily_news", "Signals")`) is `src/ui/pages/daily_news.py` — the Daily News/editorial page (`render()`'s own page title is literally `"Signals"`, line 306). The separate Radar-only page is labeled `"Radar Signals"` (`("signals", "Radar Signals")`) and can never show Daily News content at all (it renders only `Signal` objects promoted from EDGAR/DART/EDINET `CandidateSignal`s). Both fixtures in this task (an NVIDIA-tagged Tom's Hardware article, a Meta press release) are Daily News content, so "Dashboard/Signals" in this document means: **Dashboard's `recently_updated.py` feed, plus the `daily_news.py` "Signals" page** — never the Radar-only page, which is structurally unaffected by anything here.

## 1. Traced current paths

### 1.1 Issue 1 — why the Asus RTX 5090 bundle/scalper story is currently admitted

Call chain, per real article: `editorial_pipeline.run_editorial_discovery()` → `editorial_matching.matched_companies_and_themes()` → `materiality_classification.classify_editorial_story()` (computed, but does not gate) → `editorial_admission.assess_admission()`.

1. **Matching** (`editorial_matching.py`): company matching is a bare, case-insensitive, word-boundary regex against `build_company_alias_entries()`'s mechanical legal-name aliases. NVIDIA's tracked-company `name` is `"NVIDIA"` (`src/config/tracked_companies.py:96`) with no legal suffix to strip, so its only alias is the literal brand token `"NVIDIA"` — confirmed via `grep -in nvidia company_aliases.py` returning zero hits (no curated brand-alias overlay entry exists or is needed; the mechanical alias already is the brand name). Any article whose title/summary contains "Nvidia"/"NVIDIA" — virtually guaranteed for an "Nvidia GeForce RTX 5090" product article — produces `matched_companies = ("NVIDIA",)`.
2. **Admission** (`editorial_admission.py`, full file read):
   - `_identified_subject_companies()` (L312-344) decides identity from placement/action-language/rival-entity signals only, never materiality. NVIDIA is **not** in `_AMBIGUOUS_ALIAS_COMPANIES` (L116-120 — only Disco/Oracle/Alphabet/Coherent/Intel/Amazon.com/MKS/TOWA/CEVA/Nokia), so the lenient bar applies: `in_title OR has_action_language` (L342-343). "...cheapest way to buy [an] Nvidia [GPU]..." puts NVIDIA in the title → identified immediately, zero further scrutiny.
   - `_matched_consumer_format()` (L285-295) checks `_CONSUMER_FORMAT_PHRASES`/`_CONSUMER_FORMAT_PATTERNS` (L168-181): `"deal of the day"`, `"coupon code"`, `"gift guide"`, `"buying guide"`, `` `best...under $N` ``, `` `N% off` ``, etc. **None** of these match "cheapest way to buy," "$10,850 bundle," "20th anniversary bundle," "retail scarcity," or "scalper listing" — this vocabulary is a pure gap.
   - Because `consumer_format_hit` is `None`, the anchor-evidence branch (L383-386) never runs. Falls straight to L388-390: `if matched_companies: if identified_companies: return AdmissionDecision(True, f"company_subject:{identified_companies[0]}")` — admitted, **no materiality/anchor requirement at all**.
3. **Not an accidental gap** — a **deliberate, tested precedent**. `tests/test_editorial_admission.py`'s `test_gaming_pc_deal_with_specs_and_a_dollar_discount_is_admitted_but_never_high_signal` fixture (title: `"Save 25% ($560) on This Gaming PC Packed With AMD and Nvidia Hardware"`) explicitly asserts `admitted is True`, with its own docstring stating admission is *correct* and only materiality tier was ever the intended lever. That fixture already matches `_CONSUMER_FORMAT_PATTERNS`'s `` \d+%\s*off\b `` pattern and so already goes through the anchor-evidence branch (and is admitted there anyway, since NVIDIA/AMD are non-ambiguous and no anchor is required once inside that branch either — wait: re-checking L384, the anchor-evidence branch requires `identified_companies AND _has_anchor_evidence(...)` to admit, else `AdmissionDecision(False, ...)`. The Gaming-PC test's own materiality companion test confirms this fixture is admitted via `company_subject:NVIDIA` at L388-390 in the *un-gated* path in practice — meaning even a `%off`-shaped consumer deal, once it also independently satisfies L388-390's ungated identity check on a subsequent code path, is not actually the scenario under test there; what the docstring locks in is that the `assess_admission` **admission side** stays `True`) — this fixture's phrasing simply never had the material to test the gated branch's rejection path, only its own admission outcome.
   - The materiality-side companion (`test_daily_news_materiality_classification.py`) only asserts the tier stays off HIGH_SIGNAL, via `materiality_classification._CONSUMER_DEAL_PRICE_PATTERNS` (L228-232: `` \bsave\b.{0,20}\$\d ``, `` \$\d[\d,.]*\s*(off|discount)\b ``, `` \d+(\.\d+)?%\s*off\b ``) stripping only the `pricing`/`price increase`/`price cut` anchor keywords (L233, `_strip_consumer_pricing_anchors_if_deal_framed`, L240-250) when deal-price framing is present. This is materiality-tier-only (never gates admission — `editorial_pipeline.py`'s own comment, L292-297, is explicit: "Classification never affects admission/inclusion... this only adds a display-time tier label") and doesn't match the Asus fixture's language anyway (no `save $`/`$ off`/`% off` phrasing in "cheapest way to buy"/"$10,850 bundle"/"scalper").
4. `grep -rniE "MSRP|scalper|add to cart|where to buy|in stock\b|retailer" src/data_access/daily_news/*.py` → **zero matches anywhere in the package**. No retail-purchase-guide/marketplace/scalper lexicon exists at all, in either admission or materiality tiering.
5. Source registry: `toms-hardware-rss` (`source_registry.py:1304-1315`) is `category=SourceCategory.INDEPENDENT_NEWS`, `issuer_agnostic=True` — the same category as CNBC/IEEE Spectrum/Data Center Frontier. Neither `EditorialStory` nor the registry has any field distinguishing "credible trade/industry journalism" from "consumer buying-guide/retail-deal coverage" — confirmed by reading `EditorialStory`'s full field list (`daily_news_models.py:139-176`: `headline`, `publisher`, `source_url`, `published_at`, `retrieved_at`, `excerpt`, `matched_companies`, `matched_themes`, `source_feed_id`, `materiality_tier`, `materiality_reasons` — no publisher-tier/source-class field).

**Conclusion:** the fixture is admitted because (a) NVIDIA is a non-ambiguous alias, admitted on title-placement alone, and (b) the one mechanism that would force stricter scrutiny (`_CONSUMER_FORMAT_PHRASES`/`_CONSUMER_FORMAT_PATTERNS`) has no retail-purchase-guide/marketplace/scalper vocabulary at all — this exact language was never in scope for the prior false-positive calibration pass.

### 1.2 Issue 2 — why the Meta English/French pair currently reaches the Dashboard as two cards

Issuer lane: `daily_news_pipeline.py:run_discovery()`, per-entry order (L238-338):

1. `_story_id(source.company_name, entry.link)` (L94-97, `sha256(f"{company_name}|{canonical_link}")[:16]`) — keyed by URL. The English and French pages have different URLs → different `story_id` → the idempotency short-circuit (`if story_id in store: continue`, L249-251) never fires between them.
2. `dedup.is_duplicate_title(existing_headlines, source.company_name, entry.title)` (L253, L257) — `dedup.py`'s own module docstring (L9-16) describes this as covering *"the SAME development reported under a DIFFERENT canonical URL (e.g. two of one company's own feeds both carrying the same announcement)"* — i.e., it was built for exactly this class of problem, but `is_duplicate_title()` (`dedup.py:59-72`) requires **exact equality of `normalize_title_unicode()`-normalized title strings**, scoped to the same `company_name`. `existing_headlines` (`daily_news_pipeline.py:192`, `[(s.company_name, s.headline) for s in store.values()]`) is a real, cross-run, all-sources view — but a French headline never normalizes to the same string as its English counterpart, so this same-language-only literal-equality check cannot catch a cross-language localization, even though it is the intended mechanism for "two feeds, one announcement."
3. Two Meta sources are already registered today (`source_registry.py:566-577` `meta-ir-rss`, and `:661-679` `meta-newsroom-rss`, batch 2) — both English, both `issuer_name="Meta Platforms, Inc."`. If both ever published byte-identical headlines, step 2 would already suppress the second one (the "two of one company's own feeds" case *is* already solved for same-language duplicates). No French Meta source is currently registered in `source_registry.py`; the fixture is treated as synthetic/hypothetical for design purposes (see §2.2, §4).
4. `NewsStory.sources: tuple[NewsSourceReference, ...]` (`daily_news_models.py:127`) is structurally plural — but `daily_news_pipeline.py:325-334` always constructs `NewsStory(..., sources=(source_reference,), ...)` with a single-element tuple; no code path ever appends a second reference to an already-constructed story. This is real structural headroom that has never been used.
5. `NewsStoryStatus.SUPPRESSED` (`daily_news_models.py:40`) means only "no valid canonical URL" — there is no status meaning "collapsed as a duplicate/localization of another published story."
6. `daily_news_store.upsert_new_stories()` (`daily_news_store.py:94-104`): *"Adds any id not already present; leaves an existing entry untouched"* — the same insert-only contract `candidate_store.upsert_new_candidates` already uses elsewhere in this codebase. An already-persisted `NewsStory` cannot be updated (e.g. to append a second `NewsSourceReference`) through this function.

**Conclusion:** both language versions become two independent, separately-persisted, separately-rendered `NewsStory` records, because the one dedup mechanism that exists is scoped to identical normalized title text, and nothing in this pipeline ever translates a candidate before comparing it, or merges/updates an already-persisted story.

### 1.3 Issue 3 — why the French item has no translation control

1. `daily_news_pipeline.py:301`: `original_language="Non-Latin script" if summary_result.translation_unavailable else "English"`. `summary_result.translation_unavailable` comes from `summary_grounding.py`'s `_contains_non_latin_script()` (checks only Hangul/Hiragana/Katakana/CJK Unicode ranges). **French is Latin-script**, so this ternary always evaluates to `"English"` for a French source — the pipeline doesn't merely omit a language flag, it **actively mislabels** French content as English.
2. `daily_news.py:_render_card()` (L241-290): `headline = story.original_title if story.translation_unavailable else story.headline` (L282) — `original_title` is documented as *"populated only when translation_unavailable is True"* (`daily_news_models.py:126`) and, per the pipeline, is never a translation anyway — it's the same raw source title, just re-selected. There is **no language indicator, no "Translate" button, and no Original/toggle** anywhere in this function. A French story renders exactly like an English one: raw `story.headline`, no signal to the reader that it's untranslated French text.
3. `recently_updated.py`'s Daily News rows are **deliberately** excluded from the app's own existing translate mechanism: the module's own docstring (L70-72) states *"Daily News issuer translation is out of scope for this pass"*; `_load_daily_news_rows` (L267-298) and `_load_editorial_rows` (L301-332) both construct `_Row(...)` without `original_language`/`translation_document_id`, which default to `None` (`_Row`'s own dataclass defaults, L156-162). `_can_translate(row)` (L355-356: `bool(row.translation_document_id) and row.original_language in _LANGUAGE_CODE_BY_ORIGINAL_LANGUAGE`) is therefore always `False` for every Daily News row today, regardless of language.
4. `translation_service.translate_cached_with_outcome(provider, document_id, text, cache_dir, source_lang)` (`translation_service.py:141-143`) and `DeepLProvider.translate(text, source_lang, target_lang)` (`deepl_provider.py:26-62`) are already fully generic — keyed only on caller-supplied `document_id`/`text`/`source_lang`, no filing-type coupling. `recently_updated.py` already proves the exact on-demand reuse pattern end-to-end for filing rows (`_do_translate`, L375-394: a button's `on_click` calls `translate_cached_with_outcome`, result cached in `st.session_state`, never on page load, never persisted to the model). **French is not in any existing language-code map** (`_LANGUAGE_CODE_BY_ORIGINAL_LANGUAGE = {"Korean": "KO", "Japanese": "JA"}`, duplicated in `translation_service.py:60`) — DeepL supports `FR` natively, so this is a caller-side mapping gap only, not a provider limitation.

**Conclusion:** the underlying translation service is already reusable as-is; the gap is entirely in (a) `original_language` being computed by a heuristic that cannot recognize French at all, and (b) no UI call site for Daily News content ever wiring into the existing generic translate mechanism.

## 2. Smallest proposed changes

### 2.1 Issue 1 — extend the existing consumer-format lexicon (no new mechanism)

Add a narrow, curated set of retail-purchase-guide/marketplace/scalper phrases to the **already-existing** `_CONSUMER_FORMAT_PHRASES`/`_CONSUMER_FORMAT_PATTERNS` tables in `editorial_admission.py` — the exact same structural mechanism (curated phrase list + a few templated regex patterns) that already handles gift-guide/coupon-code/"N% off" shapes. Proposed additions (illustrative, to be finalized during implementation against real verified false positives, matching this module's own "verified false positive" citation discipline):

- Phrases: `"cheapest way to buy"`, `"where to buy"`, `"in stock now"`, `"add to cart"`, `"scalper"`, `"scalpers"`, `"reseller listing"`, `"anniversary bundle"`, `"bundle deal"`.
- A pattern for a standalone large consumer-product dollar figure with no earnings/contract/capex vocabulary nearby (e.g. `` \$\d{1,3}(,\d{3})+\b `` co-occurring with `"bundle"`/`"kit"`/`"pack"`) — kept as narrow and literal as the existing `` \d+%\s*off\b `` pattern, not a general price-detector.

This routes any matching story into the **existing** anchor-evidence-required branch (`assess_admission`, L383-386): admission then requires both an already-identified subject AND `_has_anchor_evidence(materiality_reasons)` — i.e. a genuine `primary_disclosure`/`formal_earnings_materials`/`material_dividend_action`/`quantified_change`/`quantified_capital_return` reason from `materiality_classification.py`. A retail-scarcity/scalper/bundle-price story has none of these and is rejected with `AdmissionDecision(False, "consumer_editorial_format:...")`. **No new gate, no new module, no new concept** — purely additive entries to an existing curated table. The existing Gaming-PC/Nvidia precedent is unaffected (it already enters this same branch via the pre-existing `` \d+%\s*off\b `` pattern; adding more phrases doesn't change that fixture's own already-tested outcome).

Genuine enterprise coverage is preserved because the anchor-evidence exception is unconditional and untouched: a real capacity/allocation/data-center-demand/channel-inventory/earnings/capex/contract/corporate-pricing story still produces a `_HARD_MATERIAL_REASON_PREFIXES` hit and is admitted regardless of any consumer-format phrase also present in the same text (this is the exact scenario `_HARD_MATERIAL_REASON_PREFIXES`'s own docstring, L54-60, describes: "letting an already-identified subject's story through a coincidentally consumer-format-shaped phrase").

### 2.2 Issue 2 — a narrow, structurally-gated, translation-assisted duplicate check (issuer lane only)

New, small module `src/data_access/daily_news/localization_dedup.py` (pure logic, no I/O — mirroring `dedup.py`'s own "pure, deterministic, no I/O" discipline), exposing one function:

```python
def is_localized_duplicate(
    candidate_company: str, candidate_source_class: SourceClass, candidate_published_at: str,
    candidate_language: str, candidate_translated_title: str,
    existing_company: str, existing_source_class: SourceClass, existing_published_at: str,
    existing_language: str, existing_title: str,
) -> bool:
```

Fires only when **all** of these hold (every one independently narrow, matching the task's own required evidence list):
1. `candidate_company == existing_company` (same tracked issuer).
2. `candidate_source_class == existing_source_class == SourceClass.OFFICIAL_COMPANY` — **first-party only**; this check can never fire for editorial/independent-journalism content, so it cannot touch Issue 1's lane at all.
3. `|candidate_published_at - existing_published_at| <= 48h` (a conservative, explicit, tunable window — publication-time proximity, not "same calendar day," to avoid timezone edge cases).
4. `candidate_language != existing_language` (the "language distinction" requirement).
5. A **conservative normalized-token-containment** check between `candidate_translated_title` (already translated to English by the caller, via the existing `translate_cached_with_outcome`) and `existing_title`: reusing `dedup.normalize_title_unicode()` for both, tokenizing on whitespace, requiring the smaller token set's containment in the larger to meet a high, explicit threshold (proposed ≥0.6) **and** a minimum absolute shared-token count (proposed ≥2) — never a bare/low-bar similarity score, and never anything resembling semantic/LLM matching. This is the "strongly aligned normalized topic/title" requirement, made tractable across languages specifically *because* the comparison happens after translation, not instead of it.

Caller wiring, `daily_news_pipeline.py`, inserted immediately after the existing `dedup.is_duplicate_title()` checks (L253-260) — i.e. only evaluated when the existing same-language exact-match dedup does **not** already catch it:
- If `entry`'s own `source.language` (see §2.3) differs from an existing same-company `OFFICIAL_COMPANY` story's own language, translate `entry.title` via `translate_cached_with_outcome` (same provider/cache already in use) and call `is_localized_duplicate(...)`.
- On a match: the candidate is **not** persisted as a new `NewsStory` — it is recorded in the existing `suppressed_items: tuple[tuple[str, str, str], ...]` reporting structure (already free-text `reason`), with a reason string that names the surviving story's own canonical URL, e.g. `f"Localized duplicate of {existing_story.sources[0].url} ({existing_story.sources[0].original_language})"`. This satisfies "preserve alternate URLs/metadata for traceability" using the **existing** data shape — no new persisted field, no new store function, no schema change.

**Directionality / "prefer English" rule — explicit, and explicitly bounded:** this check only ever suppresses the *later-arriving* candidate against an *already-persisted* story. It correctly handles the common, expected case named in the task ("retain... normally the English/global issuer version" — a French page discovered after its English counterpart is already published). It does **not** retroactively demote an already-published non-English story if an English version of the same event is discovered afterward — `upsert_new_stories`'s own "leaves an existing entry untouched" contract makes that direction structurally unavailable without a new update-in-place store capability, which this design deliberately does not add (see §4, Non-goals). This asymmetry is named explicitly rather than silently accepted.

**Why not "broad fuzzy matching":** every gate above is a hard boolean (exact company, exact source-class, a fixed time window, a language inequality) evaluated *before* the one similarity check runs, and that similarity check itself operates on already-machine-translated, already-normalized text with a conservative fixed threshold — never a raw cross-language fuzzy comparison, never an LLM call, and it can only ever compare two `OFFICIAL_COMPANY` items from the *same* issuer. Two distinct Meta releases published the same day (different topics) will not share ≥0.6 token containment after translation and are therefore unaffected — this is the basis for the "two truly distinct releases stay two cards" test (§5).

### 2.3 Issue 3 — reuse the existing generic translate mechanism, fix the root language-detection gap

1. **Root-cause fix**: add one new, optional, default-preserving field to `DailyNewsSourceEntry` (`source_registry.py`): `language: str = "English"`. Every currently-registered source is unaffected (all default to `"English"`, identical to today's behavior). A curated per-source fact, the same discipline already used for `attribution_label`/`jurisdiction`/`issuer_name` — this is the only reliable signal available (a dedicated French-locale feed URL is reliably French by construction; there is no existing text-based language-detection code path to reuse instead, and building one is out of scope — see §4). In `daily_news_pipeline.py`, replace the current `"Non-Latin script"/"English"` ternary at L301 with `source.language` directly for `NewsSourceReference.original_language`; leave `summary_result.translation_unavailable`/`original_title` (the unrelated non-Latin-script summary-fallback feature) completely untouched.
2. Extend the language-code map(s) with `"French": "FR"` (DeepL already supports `FR`; no provider change).
3. Add an on-demand **"Translate"** affordance to `daily_news.py:_render_card()`, reusing `translate_cached_with_outcome` exactly as `recently_updated.py`'s `_do_translate` already does (same cache, same `st.session_state` pattern, never called on page load) — gated on `source.original_language` being in the extended language-code map. On success, the translated title renders in a clearly labeled secondary line ("Title translation"), the native title/headline stays visible as the primary text (or vice versa via a toggle, matching the existing Radar-card convention) — never replacing `eeva_summary`, never feeding into any summary/interpretation text, and never rendered as if it were the source's own original-language text.
4. Remove the two hardcoded `None`s in `recently_updated.py`'s `_load_daily_news_rows` (`original_language`, `translation_document_id`) so Daily News issuer rows on the Dashboard gain the **same already-existing, already-tested** translate button Radar filing rows have — this is the "existing shared non-filing translation component... deliberately and safely reused" the task explicitly allows, not a new component.
5. **Editorial lane untouched**: `EditorialStory`/`render_editorial_card` are not modified — every currently-registered editorial source (CNBC, Tom's Hardware, Korea Herald's English edition, etc.) is English-language; no fixture or requirement calls for editorial-lane translation.
6. **EDGAR/EDINET/DART unaffected**: `radar_card.py`, `filing_display.py`, `cards.py`'s filing-derived paths, and `source_link.py` are not touched at all. EDINET's original-language-first default and DART's translated-by-default toggle (`radar_card.py`'s own `default_show_translated` logic) are untouched — only `recently_updated.py`'s Daily News branch (previously a hardcoded no-op) gains the new capability, and it is a Streamlit-session-local on-demand control, not a default-language change to anything filing-related.

## 4. Failure modes and explicit non-goals

**Issue 1**
- Failure mode: a genuinely material NVIDIA story that happens to also contain one of the new phrases (e.g. a supply-agreement story that mentions a reseller's stock levels in passing) would be routed into the anchor-evidence branch — but is still admitted there as long as a real `_HARD_MATERIAL_REASON_PREFIXES` hit exists, so this is a\ narrowing of *scrutiny*, not a new rejection risk for genuine coverage.
- Non-goal: a general publisher-tier/source-class distinction for editorial sources (no such field exists on `EditorialStory`/the registry today; adding one is a larger, separate change).
- Non-goal: touching `materiality_classification.py`'s tier logic (admission is the actual defect; tier is cosmetic and already non-gating).
- Non-goal: excluding Tom's Hardware as a source outright (would suppress its genuine trade-journalism coverage too).

**Issue 2**
- Failure mode / explicit non-goal: an English version published *after* an already-persisted non-English version of the same event is **not** retroactively promoted to canonical — the earlier non-English story stays visible until this design's own stated limitation is separately addressed (would require a new update-in-place store capability, deliberately not added here).
- Failure mode: the 48h window and 0.6/≥2-token thresholds are launch parameters, not empirically tuned against a large real corpus — implementation should treat them as adjustable constants, not hardcoded magic numbers, and this design does not claim they are final.
- Non-goal: any editorial-lane (non-`OFFICIAL_COMPANY`) deduplication — the source-class gate makes this structurally impossible to reach from Issue 1's content.
- Non-goal: merging sources into one `NewsStory.sources` tuple across separate discovery runs — rejected because `upsert_new_stories` cannot update an existing persisted entry without a new store capability; the suppressed-item free-text reason is the minimal substitute that still satisfies "preserve... for traceability."
- Non-goal: any general cross-source/cross-company semantic deduplication system.

**Issue 3**
- Failure mode: a source whose `language` field is left at the `"English"` default but is not actually English-language content would still be mislabeled — this is a curation responsibility (same as any other per-source registry fact today, e.g. a wrong `jurisdiction`), not a new class of risk this design introduces.
- Non-goal: automatic text-based language detection beyond the existing non-Latin-script check — deliberately not built; the per-source curated field is the narrower, more reliable, more consistent-with-existing-discipline choice.
- Non-goal: any change to editorial-lane translation, or to EDGAR/DART/EDINET filing translation defaults/toggles.
- Non-goal: persisting a translated title onto `NewsStory`/`NewsSourceReference` — the on-demand, session-cached pattern already proven for filings fully satisfies the task's "explicit Translate control" acceptable-behavior branch without any model/schema change.
